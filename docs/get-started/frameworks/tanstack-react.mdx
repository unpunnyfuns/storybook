Storybook for TanStack React is Storybook's [framework](../../contribute/framework.mdx) integration for [TanStack Router](https://tanstack.com/router) and [TanStack Start](https://tanstack.com/start/latest) applications built with [React](https://react.dev/) and [Vite](https://vitejs.dev/).

It builds on [`@storybook/react-vite`](./react-vite.mdx) to add router-aware story rendering, automatic router mocking, and mocked TanStack Start server functions. Components that depend on routing or server functions can render inside Storybook without booting your full app runtime.

## Configure

Storybook for TanStack React uses Vite through [`@storybook/builder-vite`](../../builders/vite.mdx) and automatically wraps each story in a [memory-backed TanStack Router](https://tanstack.com/router/latest/docs/guide/history-types#memory-routing). This gives you a working router context in Storybook without having to boot your full application shell.

Out of the box, it supports these workflows:

- Supply a TanStack Route to render it as the story component
- Set the initial route, params, and query string per story
- Override `loader`, `beforeLoad`, and more on the story route without modifying the original route object via `routeOverrides`
- Automatically mock `@tanstack/react-router` so router hooks resolve in stories, and record navigation from `Link`, `Navigate`, `useNavigate()`, and `useRouter().navigate` on a spy
- Opt a story into performing that navigation with `navigate`, which is off by default so stories stay on screen
- Automatically stub TanStack Start server and runtime entry points so components using server functions can render in Storybook

### Mocking

#### Automatic TanStack Router and TanStack Start mocks

This framework automatically redirects `@tanstack/react-router` imports to a Storybook-compatible mock layer. That mock re-exports TanStack Router APIs and keeps hooks such as [`useSearch()`](https://tanstack.com/router/latest/docs/api/router/useSearchHook) and [`useParams()`](https://tanstack.com/router/latest/docs/api/router/useParamsHook) resolving against the story's router.

Navigation is handled separately. `Link`, `Navigate`, [`useNavigate()`](https://tanstack.com/router/latest/docs/api/router/useNavigateHook), `useRouter().navigate`, and a `redirect()` a component receives through [`useServerFn()`](https://tanstack.com/start/latest/docs/framework/react/guide/server-functions) always record the attempt on the `onNavigate` spy, which you can import from [`@storybook/tanstack-react/spies`](#storybooktanstack-reactspies) and assert on in a play function. They only perform the navigation when the story sets the [`navigate`](#navigate) parameter. Everything else navigates whatever the parameter says, and is never recorded, because it never reaches those five entry points: a `redirect()` thrown from a loader or `beforeLoad` still redirects, as does a custom link built on [`useLinkProps()`](https://tanstack.com/router/latest/docs/api/router/useLinkPropsHook), whose returned `onClick` navigates through the real router. So do `Route.useNavigate()` and `getRouteApi().useNavigate()`, which the route binds to the router's own hook where the mock cannot reach them. On `useRouter()` only `navigate` is intercepted, so `useRouter().history.push()` navigates for real as well.

<Callout variant="warning">

**Breaking change:** the `useNavigate()` imported from `@tanstack/react-router` and `useRouter().navigate` no longer navigate by default. They used to call straight through to the real router and record nothing. They now record on `onNavigate` like `Link` and `Navigate`, and navigate only when the story sets `parameters.tanstack.router.navigate: true`. A story that calls either one and asserts on where it lands must set that parameter. A story that asserts on the spy keeps working and now also sees the attempts these two never reported. The change stops there: `Route.useNavigate()` and `getRouteApi().useNavigate()` still navigate by default and still record nothing, so a story built on those is unaffected and cannot assert on the spy.

</Callout>

For TanStack Start apps, the integration also stubs TanStack Start server and runtime entry points. This is what allows components that depend on server functions or Start-specific runtime modules to render in Storybook without a running Start server.

In practice, this means you can usually render TanStack Start components directly. A `createServerFn()` chain still exports a mock function that you can observe and override in stories and tests, and a call you do not override runs the real chain around your handler, starting with the middleware you attached to that function. See [What happens when you do not mock a server function](#what-happens-when-you-do-not-mock-a-server-function).

#### Mocking server functions in stories

If your component imports a TanStack Start server function, Storybook turns that [`createServerFn().handler(...)`](https://tanstack.com/start/latest/docs/framework/react/guide/server-functions) result into a mock function. That means you can override it per story with standard mock APIs.

A chain is only a mock when the `createServerFn` that built it came from one of the specifiers this framework redirects, `@tanstack/react-start` among them. Import it from a specifier the framework leaves alone, `@tanstack/start-client-core` for example, and you get TanStack's own builder, which no story can override. The same applies to everything else on this page that treats a server function as a mock.

#### What happens when you do not mock a server function

<Callout variant="warning">

**Breaking changes in this release**

_Unmocked server functions now run their chain._ Earlier versions replaced a `createServerFn()` chain with a mock that discarded its middleware and never touched the payload, so a call you did not override did nothing at all. Storybook now delegates to TanStack's own builder and replaces only the transport, so the chain runs. Two things to check when you upgrade:

- The `client` phase of every middleware attached with `.middleware([...])` runs on each unmocked call, so its side effects happen in stories. A middleware that throws, or that redirects, now does so in Storybook.
- The payload is serialized on its way to the handler, so a story that passes a value a real request could not carry, a callback for example, now fails where it previously went through untouched.

An unmocked call still resolves to `undefined`, because your handler body is not in the Storybook build. Stories that already override the function are unaffected, because [mocking short-circuits the chain](#mocking-short-circuits-the-chain).

_Cookie scope now matches the runtime._ `setCookie()` writes to the response and `getCookie()` reads from the request, so a value you set is no longer visible to a `getCookie()` later in the same story.

</Callout>

Storybook replaces the transport rather than the builder, so the chain a story runs is the chain your app declared, in the order it declared it. In a default build, a call you do not override runs:

- The `client` phase of each middleware passed to `.middleware([...])`, in order.
- The serialization step that would put the payload on the wire.
- A no-op spy in place of your `.handler()` body, which is why the call resolves to `undefined`.

Three things are missing from that list, because the framework removes server-only code from the build before it can reach the browser: your `.handler()` body, the `server` and validator phases of your `createMiddleware()` chains, and the validator the server function itself declares through `.validator()` or `.inputValidator()`. Input a story passes is therefore not validated. See [Running your own handler code](#running-your-own-handler-code) for what you can get back and what it costs.

##### The transport boundary

The call never leaves the browser. Where the real client would serialize the payload and send a request, Storybook serializes it and calls the server half of the same chain in process. There is no server, no request, and nothing in the network tab.

The serialization is not skipped. Both directions go through seroval with the same plugins the real transport uses, so a story cannot hand a handler a value a real request could not carry, and a handler never receives the object the story passed, only a copy of it. The pairing is not identical to the wire: the real client encodes a payload with `toJSONAsync` for the server's `fromJSON` and only encodes results with `toCrossJSONAsync` for the client's `fromCrossJSON`, while a single in-process round trip has to own both halves, so Storybook uses the `toCrossJSONAsync` and `fromCrossJSON` pair for both. `FormData` is the exception the real client also makes: it is copied rather than serialized, so `File` and `Blob` entries inside it are shared with the story instead of being rebuilt.

What comes back across the boundary only matters once there is a handler to return it, which means [`executeServerFunctions`](#running-your-own-handler-code). With that on:

- A `Response` is handed back to the caller untouched, with the `x-tss-raw` header set, as a real server does. This includes a `Response` your handler threw, which arrives as a resolved value rather than a rejection.
- A `redirect()` your handler returns or throws reaches the caller as a rejected call carrying that redirect. A redirect thrown from a middleware's `client` phase reaches the caller the same way, and that one does happen in a default build. A component that calls the function through [`useServerFn()`](https://tanstack.com/start/latest/docs/framework/react/guide/server-functions) is the exception: that hook catches the redirect and records the attempt on the navigation spy, the way a `<Link>` navigation is recorded, so assert on the spy there rather than on a rejection. Whether the story then moves depends on `parameters.tanstack.router.navigate`: left off, which is the default, the story stays on screen and the call resolves to `undefined`; set to `true`, the hook redirects through the router and the call resolves once that navigation settles.
- Streamed results are the one place a story is less faithful than the wire. A real server encodes the result as it is produced and sends it in chunks, so the caller can start reading before the handler has finished. In a story the value is resolved in full first, so a handler that returns a stream, or a promise that settles later, hands nothing back until it is complete.

##### Mocking short-circuits the chain

Overriding the exported mock replaces the whole chain, not just the handler. No middleware runs, nothing is serialized, and the value you supply is what the component receives. The [`mockResolvedValue` pattern above](#mocking-server-functions-in-stories) is unchanged.

The mock still records calls, so `toHaveBeenCalledWith` sees the arguments the component passed. Storybook resets mocks between stories, and a reset restores the real chain rather than leaving an empty spy behind.

##### Global function middleware does not run

Middleware passed to `createStart(() => ({ functionMiddleware: [...] }))` cannot run in a Storybook build. The chain reads that list at call time from TanStack's start options, which resolve through a stub that only TanStack's own compiler fills in, and that stub ships inside `node_modules`, where this framework's transforms deliberately do not reach. The list therefore always comes back empty. The `serializationAdapters` in the same options object are out of reach for the same reason, so the transport falls back to the default serializer.

Storybook logs a warning once when it is handed global function middleware, but it can only do that if something in the preview bundle evaluates your `createStart()` call, and in most apps nothing does. Assume the middleware is dropped without a warning.

Middleware attached per function with `.middleware([...])` is not affected by any of this.

To give a story the context that global middleware would have produced, set `parameters.tanstack.start.context`. Storybook merges it in exactly where the global middleware's context lands, as the base context every server function handler receives, so per-function middleware can still add to it and override it:

```ts
parameters: {
  tanstack: {
    start: {
      context: { user: { id: '1', name: 'Ada Lovelace' } },
    },
  },
}
```

Only the server half of the chain reads that context, so the parameter has no observable effect until [`executeServerFunctions`](#running-your-own-handler-code) is on. In a default build the two things that would read it, your handler body and your middleware's `server` phases, are not in the bundle.

##### Running your own handler code

By default the framework removes server-only code from the build before it can reach the browser. For server functions that means the `.handler()` body is replaced with a no-op spy, the `server` and validator phases of `createMiddleware()` chains are dropped, and so is the validator the server function itself declares.

The experimental `executeServerFunctions` framework option keeps your handler body and your middleware's `server` and validator phases, so the chain a story runs includes your own server code:

```ts title=".storybook/main.ts"
framework: {
  name: '@storybook/tanstack-react',
  options: {
    executeServerFunctions: true,
  },
},
```

The two kinds of validator part ways here, so it is worth naming which is which. A validator declared on a `createMiddleware()` chain is one of the phases the option keeps, and it runs in the server half of the call along with the rest of that chain. A validator the server function itself declares, through `.validator()` or `.inputValidator()`, is removed from the build whether the option is on or off, so the input reaching your handler is never checked against that one.

Surviving into the bundle is not the same as being safe to run there, and this is where mocking becomes a precondition rather than a convenience. Every module your handler and its middleware reach has to work in a browser, either on its own, through the TanStack packages the framework already redirects to its mocks, or through a [`__mocks__` file](#app-level-server-modules) you add for each app-level server module in the chain. A handler that reaches a database client or `node:fs` still breaks, at build time or on the first call.

Leave the option off unless you have that mocking in place. Leave it off as well when your stories already override the server functions they exercise, since the handler code is then loaded into the browser bundle without ever running.

#### Handling server-only dependencies

TanStack Start apps often import server-only packages (e.g. database clients, auth libraries) at module scope inside route files. When Storybook loads the route tree, those imports can crash the browser. The integration handles this at three layers:

##### Framework-level mocks (automatic)

The preset already intercepts `@tanstack/react-start`, `@tanstack/react-start/server`, `@tanstack/start-storage-context`, and related TanStack modules. It also removes `createServerFn()` handler bodies from the build and routes server function calls through an [in-process transport](#the-transport-boundary). You do not need to do anything for these.

##### App-level server modules

When your routes import app-specific server code (e.g. `~/db/client`, `~/auth/index.server`), use Storybook's mocking with a `__mocks__` file to prevent the real module (and its Node.js dependencies) from loading in the browser.

**Step 2**: Create `src/db/__mocks__/client.ts` next to the real module. Use only `import type` so no server packages are pulled in:

<CodeSnippets path="tanstack-react-mock-db-client.md" />

<Callout variant="info">

**Why a `__mocks__` file instead of automocking?**

[Storybook's automocking](../../writing-stories/mocking-data-and-modules/mocking-modules.mdx#automocking) replaces _functions_ but still **evaluates the original module** and its imports. For modules that import `postgres`, `pg`, or other Node.js-only packages, the original module must never be evaluated, because it would crash the browser. A `__mocks__` file is the only approach that completely prevents evaluation of the original module and its dependency chain.

</Callout>

##### Identifying what to mock

Errors like `does not provide an export named 'default'` or `AsyncLocalStorage is not defined` mean a server-only module reached the browser.

The fix is to mock the **server module itself**, not the component or route that uses it. For example, if `Dashboard.tsx` imports `~/auth/session`, and `~/auth/session` imports `~/db/client`, and `~/db/client` imports `postgres`, mock `~/db/client`.
The Node.js dependency (`postgres`) is the smoking gun; mock the closest module to it that you control.

To find that module, walk the error stack trace from top to bottom and stop at the first import you wrote yourself. Then add a [`__mocks__` file](#app-level-server-modules) for it.

Two cases where you do _not_ need a mock:

- The module is from `@tanstack/*`, which the framework preset already handles. Make sure you are on the latest `@storybook/tanstack-react`.
- The module only imports `createServerFn`, which is already mocked. The error is coming from another import in the same file.

### TanStack Query

You can use this framework together with [TanStack Query](https://tanstack.com/query) to provide a working QueryClient in Storybook and seed query data per story.

#### Project setup

TanStack Query is not automatically set up. The recommended approach is to create a single [`QueryClient`](https://tanstack.com/query/latest/docs/reference/QueryClient) in your preview file, clear it between stories via [`beforeEach`](../../writing-tests/interaction-testing.mdx#beforeeach), and share the same instance through both `parameters.tanstack.router.context` and a `QueryClientProvider` decorator.

<CodeSnippets path="tanstack-react-query-setup.md" />

This setup keeps the router context and React provider pointed at the same `QueryClient` no matter how Storybook renders the story: in the sidebar, in the Docs page, through portable stories, or in a test run. Clearing the cache before each story gives every story fresh query state while preserving one predictable integration point for loaders, route context, decorators, and story-level setup.

You can create a separate `QueryClient` for each story when you need stronger isolation, such as rendering several stories with the same query keys on one Docs page and keeping their cached responses independent. The tradeoff is that you must make the per-story client available to both the router context and the `QueryClientProvider` for that story. If those two places receive different clients, route loaders and components can read different caches, and story setup that calls `setQueryData` may not affect the component being rendered. Per-story clients also require explicit cleanup of timers, subscriptions, and cached data owned by each client.

#### Seeding query data per story

In individual stories, use [`beforeEach`](../../writing-tests/interaction-testing.mdx#beforeeach) to call [`setQueryData`](https://tanstack.com/query/latest/docs/reference/QueryClient#queryclientsetquerydata) on the shared `QueryClient` before the component renders. ## FAQ

### How do I migrate from the `react-vite` framework?

#### Automatic migration

Storybook provides a migration tool for migrating to this framework from the React (Vite) framework, [`@storybook/react-vite`](./react-vite.mdx). To migrate, run this command:

```bash
npx storybook automigrate react-vite-to-tanstack-react
```

This automigration tool performs the following actions:

1. Updates `package.json` files to replace `@storybook/react-vite` with `@storybook/tanstack-react`.
2. Updates `.storybook/main.js|ts` to change the framework property (works with both regular and CSF factories `defineMain` configs).
3. Scans and updates import statements that reference `@storybook/react-vite` in your story files and Storybook configuration files (including `@storybook/react-vite/node` used by CSF factories).
4. Detects manual TanStack Router decorators in `.storybook/preview.*`, the rest of `.storybook/`, and any `*.stories.*` file. When one is found, the CLI offers to copy a ready-to-paste AI prompt to your clipboard that walks an AI assistant through removing the now-redundant decorator.

<Callout variant="info">

`@storybook/tanstack-react` already wraps every story in a TanStack Router automatically, so any manual `RouterProvider` / `createRouter` / `createMemoryHistory` / `createRootRoute` decorator should be removed after running the automigration. For stories that need a specific route, use [`parameters.tanstack.router`](#rendering-a-route) instead.

</Callout>

### When should I use `@storybook/tanstack-react` instead of `@storybook/react-vite`?

Use `@storybook/tanstack-react` when your components rely on TanStack Router or TanStack Start APIs and you want Storybook to provide router context, typed route parameters, automatic router mocking, and mocked TanStack Start server-function behavior.

Use [`@storybook/react-vite`](./react-vite.mdx) when your app is a standard React and Vite project without TanStack Router.

### My styles are missing in Storybook

Import your application CSS in `.storybook/preview.*` so it is bundled with the preview:

```ts title=".storybook/preview.tsx"
import '../src/styles/app.css';
```

For more information, see the [styling documentation](../../configure/styling-and-css.mdx).

### How do I provide React context providers (e.g. theme, toast, auth) to all stories?

Add [project-level decorators](../../writing-stories/decorators.mdx#global-decorators) to apply providers to all stories.

You can also add [component-level decorators](../../writing-stories/decorators.mdx#component-decorators) to apply providers to all stories for a specific component, or [story-level decorators](../../writing-stories/decorators.mdx#story-decorators) to apply providers to a single story.

### Does `@storybook/tanstack-react` support React Server Components?

No. `@storybook/tanstack-react` runs stories in the browser using a memory-backed router. [React Server Components](https://react.dev/reference/rsc/server-components) require a server runtime and are not supported. If your component is a Server Component, [extract the client-side parts into a Client Component](https://react.dev/reference/rsc/server-components#adding-interactivity-to-server-components) and write stories for that instead.

### Story fails to render with an error about modules not providing a default export

This usually means a server-only module is being imported in the browser. Check the error stack trace to find the module and add a Storybook mock for it as described in [Handling server-only dependencies](#handling-server-only-dependencies).

## API

### Modules

The package exports these additional modules:

#### `@storybook/tanstack-react/react-router`

[TanStack Router](https://tanstack.com/router/latest/docs)-compatible mock implementations used by the framework to provide router behavior in stories. Import from this module when you need direct access to the mock APIs.

#### `@storybook/tanstack-react/spies`

The spies the router mock records on. It exports `onNavigate`, which is called whenever a story navigates through `Link`, `Navigate`, `useNavigate()`, `useRouter().navigate`, or a `redirect()` a component receives through `useServerFn()`, and the `NavigationEvent` type describing what it receives: the target path as `to`, plus the location navigated away from as `from` for `Link`. Import it to assert on navigation in tests, whether or not the story sets [`navigate`](#navigate).

#### `@storybook/tanstack-react/start`

[TanStack Start](https://tanstack.com/start/latest/docs)-compatible mock implementations, including a mocked [`createServerFn()`](https://tanstack.com/start/latest/docs/framework/react/guide/server-functions) implementation. Import from this module when a story or test needs to interact directly with the Start mock layer.

### Options

You can pass an options object for additional configuration if needed:

<CodeSnippets path="tanstack-react-framework-options.md" />

The available options are:

#### `builder`

Type: `Record<string, any>`

Configure options for the [framework's builder](../../api/main-config/main-config-framework.mdx#optionsbuilder). Available options can be found in the [Vite builder docs](../../builders/vite.mdx).

#### `executeServerFunctions`

Type: `boolean`

Default: `false`

Experimental. Keeps `createServerFn().handler()` bodies and the `server` and validator phases of `createMiddleware()` chains in the Storybook build instead of stripping them, so a story can run your own server code. It does not make that code browser-safe, and it does not restore the validator a server function declares on itself. See [Running your own handler code](#running-your-own-handler-code).

#### `generatedRouteTree`

Type: `string | false`

Default: `src/routeTree.gen.ts`

Path to your app's generated route tree, relative to the project root or absolute.

Storybook loads this file so that file routes reach your stories carrying the id, path and parent that the generated tree assigns them. Your app gets that by importing the tree in its entry module, which Storybook never loads, so without it a story bound to a file route renders outside its layouts and cannot resolve its own URL.

Set it to a path if your router plugin writes the tree somewhere other than the default, or to `false` to load nothing, which is what code-based and virtual routing want.

### Parameters

This framework contributes the following [parameters](../../writing-stories/parameters.mdx) to Storybook, under the `tanstack.router` namespace unless stated otherwise:

When `route` is supplied as a plain object, it may also include TanStack route options such as [`head`](https://tanstack.com/router/latest/docs/api/router/RouteOptionsType#head-method), [`search`](https://tanstack.com/router/latest/docs/guide/search-params#reading-search-params), and [`params.parse`](https://tanstack.com/router/latest/docs/api/router/RouteOptionsType#paramsparse-method).

#### `context`

Type: `Record<string, unknown>`

Router context values injected into the story router.

#### `navigate`

Type: `boolean`

Default: `false`

Whether `Link`, `Navigate`, `useNavigate()`, `useRouter().navigate`, and a `redirect()` a component receives through `useServerFn()` perform the navigation they record, or only record it. By default all five record the attempt on the `onNavigate` spy (see [`@storybook/tanstack-react/spies`](#storybooktanstack-reactspies)) and leave the story on screen. Set it to `true` and all five still record, then navigate for real, so the story renders whatever the destination route renders. Nothing outside that set is affected: `Route.useNavigate()`, `getRouteApi().useNavigate()`, `useLinkProps()`, `useRouter().history`, and a `redirect()` thrown from a loader or `beforeLoad` navigate whatever this parameter says.

Turn it on for a story that asserts on where navigation lands. Navigating to a route outside the story's mounted route tree renders a not found, as an unmatched path would in the app.

```ts
parameters: {
  tanstack: {
    router: {
      navigate: true,
    },
  },
}
```

#### `params`

Type: `ResolveParams<Path>`

Interpolates route params into the current path. When `route` is a typed file route, the type is constrained to the param names declared in that route's path (for example, `{ id: string }` for `/$id`).

#### `path`

Type: `string`

Sets the initial URL path for the story router.

#### `query`

Type: `Record<string, unknown>`

Appends search params to the initial URL.

#### `route`

Type: `AnyRoute | route options object`

Supplies a route instance directly or creates a temporary story route from route options. Storybook extracts the route's React component automatically from the route.

#### `routeOverrides`

Type: `Partial<Record<string, RouteOverrideOptions>>`

Per-route overrides keyed by route ID, applied to the story's route and root route. Use `'__root__'` to target the root route. Each entry can override `loader`, `beforeLoad`, `validateSearch`, `loaderDeps`, and `context`.

#### `start.context`

Type: `Record<string, unknown>`

Supplied under `parameters.tanstack.start`, not `parameters.tanstack.router`. The context a story provides in place of [global function middleware](#global-function-middleware-does-not-run), which cannot run in a Storybook build. Storybook merges it in as the base context every server function handler receives, so per-function middleware can still add to it and override it. Only the server half of the chain reads it, so it has no observable effect unless [`executeServerFunctions`](#executeserverfunctions) is on.

#### `useRouterContext`

Type: `({ storyContext }) => RouterContext`

Dynamically computes the router context from the story context. Use this when the router context depends on values that are already available in the story (for example, a `QueryClient` that is loaded by a story loader).

```ts
parameters: {
  tanstack: {
    router: {
      useRouterContext: ({ storyContext }) => ({
        queryClient: storyContext.loaded.queryClient,
      }),
    },
  },
}
```

This is an alternative to [`context`](#context) for cases where the router context needs a React context provider (e.g., TanStack Query's `QueryClientProvider`) that must be rendered in the story before the context value can be accessed.
